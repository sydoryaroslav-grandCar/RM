1. Статус зараз

Є

  • Скелет web-ua у репозиторії
  • Дослідження старого сайту
  • Цей план + список компонентів

Ще треба

  • Робочі мови, рамка, клієнт API
  • Компоненти й сторінки
  • Підключення даних і перевірка зв’язки
  • Зручний перегляд зібраних частин (локально / dev)

2. Принципи та до обговорення

Принцип

Єдина бібліотека компонентів

Одна кнопка, одне модальне вікно, спільні фільтри на каталогах і відгуках, кастомні списки вибору. Повний перелік — page inventory · унікальний реєстр · оцінка (D/M + delta).

Принцип

Мобільний у пікселях · десктоп у rem

Навіщо: якщо все верстати лише «сирими» пікселями під один екран, на інших моніторах (1280, 1440, 1920…) текст і відступи часто виїжджають з блоків — доводиться вручну ловити кожну ширину.

  • Телефон — своя композиція в px (зручно для тачу).
  • Планшет до редизайну — як телефон.
  • Комп’ютер — відступи, шрифти, радіуси в rem від однієї базової шкали: змінили корінь — пропорції тримаються на різних ширинах краще.
Це рішення про якість верстки (один ритм UI), не про SEO. Сайт один, HTML один.
Принцип

Калькулятор у першій хвилі

Екран і форма на фронті вже в першій хвилі. Суми рахує бекенд через API; у браузері формули не дублюємо (на старому сайті частина логіки була лише в JS — важко підтримувати).

Факт

Переходи між сторінками

На Next (App Router) переходи вже швидші за повне перезавантаження WordPress: лишається оболонка сайту, підвантажується потрібний шмат сторінки. Додатково не робимо зайвих повних reload і важких клієнтських «перемальовувань» усієї сторінки. Окремо це не обговорюємо — це нормальна робота стеку.

Узгоджено

Чат — Telegram

Швидкі UX-питання — у Telegram-чаті міграції. Учасники: уся команда.

3. Що потрібно від бекенду

Не питання «чи буде», а умова роботи фронту.

  • Опис ендпоінтів (OpenAPI / Swagger) і полів JSON для TypeScript
  • Приклади відповідей (успіх / порожньо / помилка)
  • Endpoint розрахунку калькулятора
  • У відповідях — готові URL картинок для карток і галерей

5. Етапи 1–5

Етап 1 ще треба

Підготовка проєкту

Мови (uk у корені, /ru/), рамка сторінки, ключі перекладу, клієнт API. App Router — без зайвих повних перезавантажень при навігації.

Результат: можна запускати проєкт і одразу вішати на нього компоненти з етапу 2.
Етап 2

Бібліотека компонентів

Фільтри, плашки обраних умов, пагінація, довантаження, хлібні крихти, картки, hero, слайдери, відео, модалки (у т.ч. FirstPay ~60 с), loader, empty, нотифікації, 404, шапка/підвал. Деталі — inventory · реєстр · оцінка компонентів.

Замітка

FirstPay (попап ~60 с) ≠ таймер зворотного відліку на лоті — різні компоненти.

Етап 3

Збірка сторінок

Головна, каталоги, картки авто, збережені (localStorage), відгуки, блог, контакти, пошук, VIN, оболонка калькулятора, 404. Меню на старті — тимчасовий список у коді, далі з API коли буде готове.

Етап 4

Дані з API + перевірка зв’язки

Наповнення з JSON бекенду (у т.ч. URL фото). Перевіряємо: успіх, порожньо, помилка, фільтри ↔ URL ↔ запит, пагінація/скрол, нотифікації форм.

Етап 5

Калькулятор

UI + виклик API розрахунку: показ результату або зрозумілої помилки.

6. Середовище для перевірки готових частин

Потрібно зручно відкривати вже зібране (локально або спільний dev/preview), а не «порожній каркас для галочки».

  • Спочатку — локальний запуск + preview гілки за потреби
  • Коли є перші екрани — спільний URL для команди
  • CI на pull request — разом із регулярними збірками

7. SEO у верстці

Опираємось на SEO-аналітику аудиту сайту (жовтень 2026) і вимоги з неї для шаблонів сторінок. Джерело: Google Doc — SEO-аудит / аналітика (локальна копія також у assets-from-production/ як файл аудиту .docx).

  • Один H1; title / description з даних API
  • Один canonical; hreflang uk ↔ ru у шапці HTML
  • Розміри картинок, lazy, пріоритет головного фото
  • Schema з полів API — за шаблоном з бекенду

8. Паралельно: Google Search Console (не етап фронтенду)

Карта сайту (sitemap) уже зібрана з продакшену (~1.4M URL). Чого ще немає — картина індексації в Google. Без цього важко безпечно вимкнути WordPress. Фронт цим не верстає й не чекає на етапи 1–3.

Запит до команди (достатньо файлів, постійний доступ у акаунт не обов’язковий)

  • Індексація → Сторінки — повний експорт (що Google бачить / виключає)
  • Ефективність → Сторінки — кліки, покази, CTR, позиція (максимальний період)
  • Карти сайту — статус підключених sitemap (скрін або список)

Куди покласти: assets-from-production/gsc/. Далі SEO + бекенд будують матрицю URL (залишити / редирект / прибрати) перед перемиканням домену.

Замітка

Це паралельний запит до cutover, не задача збірки компонентів. Збірка UI йде незалежно; експорт GSC потрібен до дня переїзду.
